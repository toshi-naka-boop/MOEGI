### [C-11] 種別: 実装 / 深刻度: high
**指摘: gemma4:26b は reasoning モデルであり、`llm.py` が使っている呼び出し経路では出力が全部 `reasoning` に流れて `content` が空になる。N-11 のモデル変更をこのまま実装すると、日報エージェントもオフライン fallback も全件が空応答＝判定不能になる。**

破綻シナリオ:
`llm.py::_call_local` は Ollama の OpenAI互換 `/v1/chat/completions` に `max_tokens`（models.toml の `max_output_tokens`: matching 900 / draft 700）を付けて投げ、`data["choices"][0]["message"]["content"]` をそのまま読む。この経路で gemma4:26b を実測した結果:

| 条件 | finish_reason | completion_tokens | content 長 | reasoning 長 | 所要 |
|---|---|---|---|---|---|
| 現行コードと同じ（`max_tokens=900`） | length | 900（全消費） | **0** | 2517 | **21.4秒** |
| ネイティブ `/api/generate`・num_predict=1500 | length | 1500（全消費） | **0** | — | 40.2秒 |
| `reasoning_effort:"none"` 追加・`max_tokens=900` | stop | 372 | **844（正しいJSON）** | 0 | **約10秒** |

（プロンプトは §6.5 `structure()` 相当の日報構造化・チェックリスト9項目・発話1文、266 prompt tokens）

つまり現行実装のまま `models.toml` の local モデルを差し替えると、**呼び出しは成功扱いで返るのに本文が空**になる。パイプラインは `_undecidable_impact` か JSON パース失敗に倒れ、承認UIは「判定不能」で埋まる。日報側は `structure()` が何も返さないので G6 の落ちが出ない。timeout ですらないので §6.6 の「判定不能として続行」は機能するが、画面には何も立たない。

さらに波及する:
- **R-70（gemma4:26b は 1呼び出し平均70秒・再現率16.7%）の測定はこの機構の影響を受けている可能性が高い。** 実測では 26B は 42 tok/s 出ており、遅いのは reasoning トークンを吐いているからで、モデル自体が遅いのではない。
- したがって design.md §6.3 の断定「**モデルを大きくしても頭打ちになる——ボトルネックは逐語引用の安定性であり、モデル容量の問題ではない**」は、根拠が不安定なまま結論だけが本文に据わっている。N-10（evidence を ID 参照方式へ）適用後に gemma4 を測り直してもいない（§6.3 の 26B 行は N-10 前の数字）。
- v13案が「gemma4:26b は遅いので台本タイミングが要検証」と自己申告している**リスクの定義そのものが外れている**。真のリスクは速度ではなく「出力予算が思考に食われて本文ゼロ」と、下記 C-14 のメモリ。

提案:
1. `_call_local` に `reasoning_effort: "none"`（Ollama の OpenAI互換エンドポイントで有効。`think:false` は**無視される**ことを実測済み）を付けるか、`message.reasoning` を捨てて `content` だけ読む前提を明示的にテストで固定する。
2. その上で R-70 を再測してから、§6.3 の「モデルサイズでは解けなかった」を残すか消すか決める。今の書き方は、後から「実は設定ミスでした」となったときに ①⑤⑥ の主張ごと巻き添えになる。

### [C-12] 種別: 前提 / 深刻度: high
**指摘: 「SiteDoc/ChecklistItem は項目ラベルのテンプレート定義であり患者個人に紐づく情報を一切含まない」は、design.md 自身の §6.4・§6.5 と矛盾している。ChecklistItem は `goal_ref`（利用者の看護目標）を運ぶ設計になっており、これは要配慮個人情報になり得る。**

根拠（すべて design.md / 実コード内）:
- §6.4: `ChecklistItem 項目 { sitedoc_id, label, kind(自由記述|選択|評価), goal_ref?, required }`
- §6.5: `goal_ref: 参照した看護目標（**setChecklist 経由で渡る**） ← 必須`
- G6 の合格条件（§3・R-30）: 「評価が**その利用者の看護目標を参照して**生成されていること」
- `src/moegi/pipeline.py:53` に `goal_ref: str | None`、`config/sitedoc_sample.toml` に項目「利用者の看護目標」

看護目標は「特定の利用者の療養上の目標」＝ 病状・心身の状態に関する記述であり、氏名や利用者IDと結びついた時点で要配慮個人情報の側に落ちる。**「事業所文書か否か」ではなく「テンプレートか実インスタンスか」で線が引かれるべきで、v13案はそこを取り違えている。** SiteDoc.kind には「手順書」も含まれる（§6.4・§1）が、実運用の手順書・運営規程には個別事例や利用者名が紛れ込む余地がある——という批評依頼の懸念は、より近いところで既に実現している。

破綻シナリオ:
D6 で「接続点1箇所（承認済みチェックリスト → 日報）」を繋ぐとき、G6 を満たすには `goal_ref` に実際の看護目標が入る。その同じ SiteDoc が次の通達更新で ③-b にかかると、患者の看護目標がそのままクラウドのゲートウェイに出る。しかも今それを止めているのは設計上の保証ではなく、`_format_items()` が `label` と `kind` しかプロンプトに詰めていないという**実装の偶然**である。誰かが「判定精度を上げるために項目の付帯情報も渡そう」と1行足した瞬間に境界が破れ、テストは通る。

これは round-1 X-2 で「モードでなく**構造**で保証する」と決めた性質そのものの後退である（X-2 は解決済み索引にあるが、v13案が前提を差し替えたので新しい根拠として再提起する）。v12 までは「SiteDoc が入る工程はローカル」という**型で判定できる**不変条件だった。v13案は「入っている**中身**に要配慮個人情報がないこと」という、コードでは検査できない条件に置き換わっている。

提案:
- クラウドへ出す直前に通す射影を1箇所に固定する（例: `ChecklistItem.to_cloud_payload() -> {label, kind, required}`）。`goal_ref` や将来追加されるフィールドは**明示的に列挙しない限り出ない**構造にし、「payload に goal_ref が含まれないこと」をテストで固定する。これで v13 でも「構造で保証」を維持できる。
- §6.1 の表の「入力に要配慮個人情報を含むか ✗」は、**その射影を通した後の話であること**を本文に書く。今の書き方は「SiteDoc には元々入っていない」と読め、事実と違う。
- 併せて「手順書（SiteDoc.kind=手順書）は自由文なので射影で守れない」ことを認め、デモ範囲がチェックリストのみである旨を §4 に明記するか、手順書は既定ローカルのままにする。

### [C-14] 種別: 設計 / 深刻度: high
**指摘: gemma4:26b は 17GB。Tanuki 6.2GB と併存できず、§6.2 の D1 同時常駐実測（Tanuki 6.5GB + faster-whisper、スワップ 2.3GB）は 26B 前提では無効になる。にもかかわらず再実測タスクがどの日にも計上されていない。**

実測（本レビュー中）:
- `ollama list`: `gemma4:26b` 17GB / `7shi/tanuki-dpo-v1.0` 6.2GB / `gemma4:e2b` 7.2GB
- gemma4:26b の**コールドロード 18.1秒**（`load_duration`）。ウォーム時は 0.25〜0.3秒
- 現時点の実機: `hw.memsize` 24GB に対し `vm.swapusage used = 6.09GB`、free pages 約350MB（本レビュー時点の常用状態）

破綻シナリオ:
1. **モデル併存が物理的に不可能**。17GB + 6.2GB = 23.2GB。ここに faster-whisper・FastAPI・ブラウザ・Ollama の KV キャッシュが乗る。オフライン fallback（③-b/④）に Tanuki を残す案（§6.1 の「要検証」注記に挙がっている）は、24GB では成立しない。Ollama がどちらかを退避するので、**切替のたびに 18秒のロードが入る**。
2. **台本の並びが最悪の順序**。§7 は #6（日報＝gemma4:26b）→ #7（Wi-Fi断、③-b/④ がローカルへ）と連続する。ここでモデルが変わると 10秒枠に 18秒のロードが割り込む。§7 の注記「待ち時間は説明の枠として使う」は 8.4秒（R-54）を前提に書かれた文で、18秒＋推論は別の話。
3. **D1 ゲートの結論が失効している**。§6.2 の表「ASRとLLMの同時常駐 ✅ 成立」「ASR並走時の劣化 +10.1%」「スワップ 2.3GB」はすべて 6.5GB モデルの値。§4 の撤退ライン「ASRとLLMが同時常駐できるか → 載らないなら ASR を優先し LLM を小さくする。それでも駄目なら G6・G7 を撤退」は、26B では**判定をやり直さないと撤退可否が決められない**。§10 の D1 行は「✅完了」のままで、再実測はどの日にも入っていない。D5 は「日報・1日厳守」なので、当日ここで詰まると即撤退分岐に入る。

提案:
- **ローカルは1モデルに統一する**（日報もオフライン fallback も同じモデル）を先に決める。併存前提の記述（§6.1 の要検証注記）は物理的に選択肢でないので落とす。
- 統一するモデルの候補比較を D5 着手前の 30分タスクとして §10 に立てる: 26B（17GB・reasoning あり・C-11 の設定が要る）vs `gemma4:e2b`（7.2GB）vs 現行 Tanuki。判定軸は「§6.2 の同時常駐 3項目の再実測」＋「structure() 1回の実測秒数 × 2回（§7 の Before/After は**同一発話を2回 structure() に通す**設計なので呼び出しは2回になる）」。
- ウォーム維持（`keep_alive`）を運用手順に入れる。既定 5分でアンロードされると、ブースの待ち時間中に 18秒のロードが復活する。(a) 30秒復旧台本に1行足す性質の話。

## 補足: 依頼の観点1（法的・実務的な見落とし）についての所見

「事業所チェックリストのテンプレート定義は要配慮個人情報に該当しない」という**限定された命題そのものは妥当**である。要配慮個人情報は「特定の個人を識別できる情報のうち、病歴・心身の機能の障害等を含むもの」であり、項目ラベル（「バイタルサインの記録」等）は個人と結びつかない。`config/sitedoc_sample.toml` の現物も純粋なラベル集合で、実際に患者データを含まない。

見落としは**法解釈側ではなく、design.md 側の「テンプレート」という語の使い方**にある:
1. **C-12 のとおり `ChecklistItem` は実インスタンス（`goal_ref`）を運ぶ設計になっている。** 「テンプレート定義である」は現在の fixture の性質であって、データモデルの不変条件ではない。
2. `SiteDoc.kind` には**手順書**が含まれる。手順書・運営規程は自由文で、実運用では個別事例（「◯◯様の場合は…」）が混ざる余地がある。デモ範囲がチェックリストのみであることは §4 に書かれていないので、命題が手順書にも及ぶように読める。
3. §9・§13 は「**実運用では事業所内で完結します**」と実運用を語っている。デモの fixture が安全であることと、製品として安全であることを、同じ1文で主張している状態になる。

つまり訂正の方向は正しいが、**「だから構造上出ない」ではなく「出さないための射影を1箇所に置く」**という実装の裏づけを足さないと、v12 が持っていた保証の強度（型で検査できる不変条件）を失ったまま主張だけが残る。
