# プロンプト文面レビュー（`_MATCH_ITEM_PROMPT` / `_ORCHESTRATE_PROMPT`）

## Round P1 — 2026-08-12 — 工程: 批評（プロンプト文面のみ／設計の是非は対象外）

対象: `/Users/toshixa/MOEGI/src/moegi/pipeline.py` L315-339（`_ORCHESTRATE_PROMPT`）、L365-395（`_MATCH_ITEM_PROMPT`）。
比較対照として L770-800 の `_MATCH_BATCH_PROMPT`、および `_orchestrate_duplicate_candidates`（L342-362）・`_recover_trailing_fields`（L435-459）の応答パース挙動を併読した。

観測事実（依頼元より）: 弱い指示のみ 再現率83.3% / 誤検出13.7% → オーケストレーション追加で 70.9% / 11.3%。
**誤検出はほぼ動かず再現率だけが12.4pt落ちている**＝オーケストレーションは「重複を選んで消している」のではなく「候補数を無差別に削っている」挙動に近い。以下はその文面上の原因分析。

---

### 指摘

- [C-1] 種別: 実装 / 深刻度: high
  - 指摘: `_ORCHESTRATE_PROMPT` は「刈り込みは正しい」という事前分布を冒頭で植えた直後に、熟考トークンを1つも挟まず `keep` 配列を最初のキーとして出力させている。除外判断が推論ではなく事前分布のサンプリングになっている。
  - 破綻シナリオ: 出力形式は `{"keep": ["1", "3"], "rationale": "判断理由をここに"}`。JSON はキー順に生成されるため、モデルは **`keep` を書き終えてから `rationale` を書く**。つまり除外の是非を考える前に除外結果が確定している。その「考える前の状態」を作っているのが冒頭2〜4行目「実際にはそのうち一部だけが本当に固有の文言変更を必要としていて、残りは既に他の項目でカバーされている（重複している）可能性があります」——これは指示ではなく**前提の断定**であり、しかもこのプロンプトは `len(candidates) >= 2` のときしか呼ばれない（L700）ので、**呼ばれる度に必ず「この中に重複がある」と言われる**。1つの要求事項が正当に3項目へ影響するケース（--label d の正解2項目のような）でも、モデルは最初のトークンで1〜2件に削る。後段の `rationale` は削った後の後付け正当化にしかならないため、「見逃しの方が問題」という注意書きが効く余地が構造的に無い。
  - 提案: (1) 冒頭を対称な記述に変える:「1つの通達変更が複数の項目にそれぞれ実質的な文言変更を求めることは普通にあります。一方で、独立判定は他項目が見えないため、同じ根拠文から同じ内容の変更を複数項目が重複して主張してしまうことがあります。この重複だけを取り除くのがあなたの仕事です。」 (2) 出力キー順を逆にし、候補ごとの検討を先に書かせる:
    ```
    次のJSONオブジェクトのみを出力すること。キーはこの順序で書くこと。
    checks: 候補1件ごとに1要素。{"no":"1","keep":true,"why":"残す/除外する理由"}
    keep:   checksでkeep=trueにした番号だけを文字列配列で入れる
    ```
    なお `_orchestrate_duplicate_candidates` は `keep` が list で無い／パース失敗時に **候補をそのまま返す**（L357-359）ため、長文化して途中切れしても安全側（全件保持）に倒れる。単発判定側（C-4）と違い、この順序変更は再現率を下げるリスクが無い。

- [C-2] 種別: 実装 / 深刻度: high
  - 指摘: 【指示】の中核文「その中で**最も直接的に対応する項目だけを残し**、他は重複として除外してください」が、タスクを「各候補が本当に必要か」という**絶対判定**から「どれが一番それらしいか」という**相対ランキング**にすり替えている。ランキングは定義上必ず敗者を出すので、正当な複数項目影響が常に1件へ潰れる。
  - 破綻シナリオ: 発火条件である「複数の項目が同じ内容を重複して主張している場合」に定義が無い。候補は全て**同一の `requirement_text` から導かれた rationale** なので、語彙レベルでは常に「同じ内容を主張」しているように見える（例: 「開始・終了時刻の記録が求められるため」が訪問記録票の項目でも訪問日数・頻度の項目でも書かれる）。よって曖昧な発火条件が実質常時 true → 「最も直接的な1つだけ残す」が実質常時適用 → 3候補が1候補になる。再現率だけが落ち誤検出が動かない実測パターンと一致する。安全弁の「**判断に迷う場合は残してください**」は太字だが、(a) 刈り込み命令より後ろに置かれ、(b) 「迷う」という**内省状態の自己申告**を条件にしている。LLM は迷いを申告せず自信ありげな rationale を書くので、この分岐はほぼ発火しない。
  - 提案: 相対比較をやめ、除外を客観的なチェックリスト（AND条件）にする。内省ではなく事実で判定させる:
    ```
    【除外してよいのは、次の3つがすべて言い切れる候補だけ】
    1. 残す候補と同じ根拠文（S番号）にもとづいている
    2. 残す候補の項目文言を直すだけで、この要求事項が現場で満たされる
    3. 除外する候補の項目文言は一切変えなくてよい
    1つでも言い切れない候補は残すこと。「どちらがより直接的か」で選ばない
    （複数の項目がそれぞれ別の文言変更を要するなら、全部残すのが正解）。
    ```

- [C-3] 種別: 実装 / 深刻度: high
  - 指摘: `candidates_block` に渡している情報が `f"{i}. 項目「{c.sitedoc_item_id}」: {c.rationale}"`（L351）だけで、**重複／非重複を分ける最強のシグナルである evidence（根拠文IDと原文）を捨てている**。結果、モデルは「rationale 同士の文面的な似ている度」で重複を判定するしかない。
  - 破綻シナリオ: 候補A が S2（開始・終了時刻の記載）を、候補B が S5（訪問頻度の記載）を根拠に要更新になっていても、両者の rationale は同じ要求事項の言い換えなので文面が似る。モデルには S2/S5 の違いが**見えていない**ため、根拠文が別＝独立した変更が必要という決定的事実を使えず、片方を重複として落とす。これは N-10 で「根拠文IDが実在する文を指す」ことをコード側で保証した投資（L638-640）を、オーケストレーション段で丸ごと捨てていることになる。項目の `kind` も渡っていないため、種別が違う（記録票 vs 手順書）候補も区別できない。
  - 提案: ブロックを情報量のあるものに変える。`Impact.evidence` は `notice_section_path` / `quote` / `offset` を持つ（L87-92）ので、生成時に `evidence_segment_id` を保持しておくか `quote` をそのまま出す:
    ```python
    f"{i}. 項目「{c.sitedoc_item_id}」（種別: {kind}）\n"
    f"   根拠文: {c.evidence[0].quote}\n"
    f"   判定理由: {c.rationale}"
    ```
    その上でプロンプトに一文追加: 「**根拠文が異なる候補どうしは重複ではない。除外の検討対象は、同じ根拠文を引いている候補の組だけに限ること。**」 これだけで、根拠文が割れているケース（正当な複数項目影響の典型）が機械的に保護される。

- [C-4] 種別: 実装 / 深刻度: mid（再現率の不安定さの主因候補）
  - 指摘: `_MATCH_ITEM_PROMPT` には **「要更新」の定義が1行も無い**。一方 `_MATCH_BATCH_PROMPT` には【判定の基準】として運用可能な定義がある（L775-777:「"要更新" は、この通達変更が要求する内容を書き加えないと、その項目が通達に適合しなくなる場合だけ」「項目の書き方が良いか悪いかは判定の対象ではない」「1つの通達変更が関係する項目はふつう少数」）。ledger N-8 が自ら「単発モードのプロンプトは未対応」と書いた欠落が、兄弟項目の追加では埋まっていない。
  - 破綻シナリオ: 判定基準が無い状態で兄弟項目リストだけを渡し、その使い方として与えているのが「機械的に「影響なし」に倒す必要はない——同じ通達内容が複数の項目にそれぞれ実質的な変更を要求することもある」という**否定形の注意書きだけ**。「何をするな」は書いてあるが「兄弟リストを何に使え」が書かれていないため、各サンプルがその場でルールを発明する＝出力分散が上がる。単発計測では改善して4回平均では不安定、という観測はこの分散増加と整合する。さらに兄弟項目は**ラベルのみを「、」で連結した1行**（`_format_other_items_block` L287-290）で、他項目の判定結果も本文も渡っていないため、「他項目がカバーするか」はそもそも判断材料が不足しており、モデルの推測に依存する。
  - 提案: (1) batch と同じ【判定の基準】を移植し、判定を単一の絶対問に固定する:
    ```
    【判定の基準】
    - "要更新" は、この要求事項が求める内容を書き加えないと「{item_label}」が通達に適合
      しなくなる場合だけ。項目の書き方の良し悪しや、記録が実際に行われているかは対象外。
    - 判定は次の一問だけで決めること:「{item_label}」の現在の文言のままで、この要求事項を
      満たしていると言えるか。言えないなら "要更新"、言えるなら "影響なし"。
    ```
    (2) 兄弟項目リストの用途を明示する: 「他の項目は、要求事項のどの部分がどの項目の担当かを切り分けるための参考にすること。**他の項目の方が適切に見えるという理由だけでは "影響なし" にしない**（その判断は後段でまとめて行う）。」——重複除去の責務を後段に一本化し、単発側で抑制がかからないようにする。現状は単発側とオーケストレーション側の**両方が同じ曖昧な相対判断を行っており、抑制が二重にかかっている**。83.3%→70.9% の追加低下はこの二重適用として説明できる。
  - 補足（やってはいけない改善）: 単発側は `verdict` を先頭キーにする現行順序を**維持すべき**。`_recover_trailing_fields` の docstring（L438-441）が記録している通り、ローカル8Bは rationale 直後で早々に `}` を出す崩れ方をする。ここで rationale を先頭に移すと、途中切れ時に `verdict` が生成されず `entry.get("verdict") != "要更新"` で**黙って影響なし扱い**（L681）になり、再現率がさらに落ちる。C-1 の順序変更はオーケストレーション側（失敗時に全件保持へフォールバックする）に限定する。

- [C-5] 種別: 実装 / 深刻度: mid
  - 指摘: `_ORCHESTRATE_PROMPT` の唯一の出力例が `{"keep": ["1", "3"], "rationale": "..."}` で、**「何かを除外した結果」だけを実演**している。加えて「重複が無ければ全番号を残すのが正常な結果」という記述がどこにも無いため、null action（何も除外しない）が非正規な出力に見える。
  - 破綻シナリオ: (a) 候補が2件のとき、唯一の例が `["1","3"]` なので番号3という**存在しない番号**を返す模倣が起こりうる。そのとき `kept = [c for i, c in enumerate(candidates, 1) if str(i) in keep_indices]`（L361）は範囲外番号を黙って捨て、**候補2が理由なく消える**。`kept` が空でない限り L362 のフォールバックは働かないので、この誤りは検出されず再現率だけが落ちる。(b) 例示バイアスにより「1件も除外しない」応答が出にくくなる。few-shot が1つしか無い場合、モデルはその形を強く模倣する。
  - 提案: 候補数を本文に埋め込み範囲を明示し、null action を正常系として例示する:
    ```
    keepには1〜{n}の範囲の番号のみを入れること（存在しない番号を書かない）。
    重複が無ければ1〜{n}を全部入れる。それは正常な結果である。

    出力例1（重複が無く全部残す場合）: {"checks":[...], "keep": ["1","2","3"]}
    出力例2（2が1と重複していた場合）: {"checks":[...], "keep": ["1","3"]}
    ```
    併せてコード側で範囲外番号を検出したら候補をそのまま返す（`if not keep_indices <= {str(i) for i in range(1, len(candidates)+1)}: return candidates`）ことを推奨。プロンプト逸脱が静かな見逃しに化ける経路を塞ぐ。

### 全体の重み付け（文面上の賛否バランス）

`_ORCHESTRATE_PROMPT` を「刈り込みを促す記述」と「保持を促す記述」に分解すると:

| 方向 | 記述 | 位置 |
|---|---|---|
| 刈り込み | 「実際にはそのうち一部だけが本当に…残りは既にカバーされている」 | 冒頭（primacy・タスクの枠組み自体） |
| 刈り込み | 「最も直接的に対応する項目だけを残し、他は重複として除外してください」 | 指示の主動詞 |
| 刈り込み | 出力例 `["1","3"]`（除外を実演） | 唯一の few-shot |
| 刈り込み | `keep` が先頭キー＝熟考なしで決定 | 出力形式 |
| 保持 | 「判断に迷う場合は残してください」 | 指示の後半・内省条件で発火しにくい |
| 保持 | 「見逃しの方が重複より問題が大きい」 | 括弧内の補足 |

刈り込み側は**タスクの枠組み・主動詞・唯一の例・生成順序**という強い位置を全て占め、保持側は**補足と内省条件**という弱い位置にしかない。「弱い指示」のつもりで書かれた文面が、構造上は強い刈り込み指示になっている。実測（再現率-12.4pt / 誤検出-2.4pt）はこの非対称そのもの。

C-1〜C-3 と C-5 を適用しても再現率が回復しないなら、それは文面ではなく**このアーキテクチャ（rationale だけを見て事後に消す）が目的に合っていない**ことの証拠になる。その場合の代替は、オーケストレーションに「消させる」のをやめ、`{"duplicate_groups": [["1","2"]], "reason": ...}` の形で**重複の疑いを申告させるだけ**にして、実際に消すか否かは承認UI（人間のゲート）に委ねる方式。design.md の「人間が承認画面で絞る」という既定路線（ledger N-8 の位置づけ）とも整合し、自動除外による見逃しリスクをゼロにできる。
