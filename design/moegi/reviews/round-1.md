## 指摘

### [C-1] 種別: 設計 / 深刻度: high

- **指摘**: 数百ページ規模の新旧留意事項通知から「適正な訪問看護の推進」の3項目だけを取り出す**絞り込みの実装位置が設計書のどこにも定義されていない**。§2は「範囲が狭いので8日間で精度を作り込める」と主張するが、その狭さを実現する処理が §6 のパイプラインにも §6.4 のデータモデルにも存在しない。

- **破綻シナリオ**:
  - §6.1 の ①取込・正規化は「LLM不使用（規則）」、②差分抽出は「構造化済みテキストの差分整形」と定義されている。この定義に従うと、②の出力 `Change[]` は**新旧通達の全差分**になる。保医発系の留意事項通知は改定のたびに文言修正が全編に散るため、Change は数百件のオーダーで出る。
  - するとD2の完了条件「CLIで通達ペアを食わせると『適正な訪問看護の推進』の更新案がJSONで出る」を満たすには、その数百件のうち3項目だけを選ぶ工程が必要になる。選択肢は3つあり、どれもD2の工数と§6.1の主張を変える:
    - (a) ①取込時にセクションパスでハードコード切り出し → 「通達を丸ごと食わせたら追従する」というデモの主張が崩れる（審査員に「これ範囲決め打ちですよね」と1問で崩される）
    - (b) ②差分抽出後にLLMで改定項目分類 → 安価モデル1工程が増え、数百件分のトークンが走る。§6.1のルーティング表にない工程がD2に丸ごと追加される
    - (c) ③影響判定に全Changeを流す → 高精度モデルに数百件×チェックリスト項目数の呼び出しが走る。デモの1回実行が数分〜十数分になり、G1（中断なく1回実演）とデモ台本#4（10秒）が同時に死ぬ。原価も§6.3の「通達1本あたり◯円」が桁違いになる
  - さらにD1の完了条件は「新旧PDFが手元」までで、**①取込・正規化の完了条件が書かれていない**（D1の内容欄には⑥として入っているのに、完了条件欄に対応する記述がない）。厚労省PDFは2段組・表組みが混在しテキスト抽出でレイアウトが崩れるため、条・項・別表の決定的パースは実際にはD1で最も時間を食う工程になりうる。ここが半日ずれるとD2の3工程＋アダプタ層が丸ごと押し出され、D3-4の承認UI（②⑦の核・R-7で前倒し固定済み）に食い込む。

- **提案**:
  - 絞り込みを「**①取込時のセクション限定 ＋ その事実を画面で明示**」に固定し、design.md に明文化する。デモでは「今回は『適正な訪問看護の推進』の節に限定して取り込んでいます」と**先に言い切る**方が、後から突かれるより強い（§5.1で「言えないことを言わずに済む」を採ったのと同じ論法）。
  - D1の完了条件に「①取込・正規化の完了条件」を明示する（例: 新旧それぞれから対象節の Section[] が JSON で出て、`path` が新旧で対応づく）。
  - D1が6項目あるのは §10 の「D1に判断と調達を集中させる」原則の裏返しで、調達・セットアップ（②③④⑤）と実装（①⑥）が同居している。**①取込・正規化はD2の頭に移す**か、逆にD2の「LLMアダプタ層」をD1の夜に前倒しする（アダプタは20〜30行の薄いラッパで、ORCA/Ollamaの疎通確認がD1の③と同じ作業だから合流できる）。現状のD1/D2境界は作業の性質で切れていない。

### [C-2] 種別: 設計 / 深刻度: high

- **指摘**: デモ台本（§7）の秒数が**LLM推論・ASR推論の実行時間をゼロと仮定**しており、加えて表の秒数を合計すると**75秒**で、見出しの「約60秒」と一致しない。

- **破綻シナリオ**:
  - 算術: 前半 5+10+5+10+5+10 = **45秒**、後半 10+5+5+5+5 = **30秒**、合計 **75秒**。見出しの「約60秒」は表と合っていない。§8③の「触れて数十秒で価値がわかる」の根拠が数字として崩れている。
  - より重いのは中身。各ステップの秒数は**司会の喋り時間**であって処理時間を含んでいない:
    - **#4（10秒）**「差分 → 影響判定 → 更新案。原文トレースを1回見せる」— 安価LLM1工程＋高精度LLM2工程がネットワーク越しに直列で走る。高精度モデルの生成が各工程で数百〜千トークン出るなら、往復込みで数十秒。10秒に収まる見込みはない。
    - **#7（10秒）**「Wi-Fiを切る → 全工程がローカルへフェイルオーバー → パイプラインが完走」— Ollama 8B クラスをラップトップで回すと生成速度は数十 tok/s のオーダー。影響判定＋更新案で合計1000トークン前後出れば**それだけで20〜40秒**。しかも §6.2 が自ら「起動時ロード時間をブースの体感に含めて実測する」と書いており、初回は 4〜5GB のウェイトロードが上乗せされる。**設計書自身が「体感に含める」と認めている時間が、台本には1秒も計上されていない。**
    - **#2 / #6（各10秒）** — ローカルASRの文字起こし＋LLMによる構造化。whisper系のローカル推論は発話長の数分の一〜同程度の時間がかかる。「喋る→出る」が10秒で閉じる保証がない。
  - 結果として起きること: 実際の1周が2〜3分になる。回遊形式の審査員は**処理待ちの無言の20秒で離脱する**。ブースで最も高い代償を払うのは、失敗ではなく**沈黙**。
  - さらに、待ち時間を隠すために「過去実行結果のローカルキャッシュ」（§7末尾に1行だけある）を使うと、今度は「今計算した」感が消えて③④が弱る。このトレードオフが設計書で扱われていない。

- **提案**:
  - 台本の各ステップに「**喋り秒数 / 処理秒数**」の2列を持たせ、D7の実測でこの表を埋めることをG3の確認手順に含める。実測前の見積もりは全部仮の数字であると明記する。
  - 処理待ちを**設計として演出に変える**: 工程ごとの逐次表示（①取込済 → ②差分3件 → ③影響判定中…）とストリーミング出力で、待ち時間中も画面が動き続ける状態にする。無言の待ちをゼロにするのが目的で、これは実装コストが小さい割にブースでの効き方が大きい。
  - 前半（オンライン）と後半（オフライン）を**別々のループとして独立に回せる**構成にする。回遊審査は審査員が途中から来て途中で去るので、75秒の一本道は前提として危うい。「30秒の紙ループ」と「30秒のオフライン→復帰ループ」の2本立てにすれば、どこから来た審査員にも完結した弧を見せられる。
  - 見出しの「約60秒」を実測後の数字に直す。

### [C-3] 種別: 設計 / 深刻度: high

- **指摘**: ブースで口にすることになっている**数字がひとつも設計書に定義されておらず**（②の金額、①の一次情報の具体値、⑥⑦の「精度が◯%落ちます」）、その数字を作る作業が **D1〜D8に1コマも割り当てられていない**。

- **破綻シナリオ**:
  - **⑥⑦の精度差**: §6.3は「影響判定の一致率」を実測して並置すると書くが、**一致率の分母＝正解データが存在しない**。「クラウド出力とローカル出力の一致率」なのか「人が作った正解との一致率」なのかも表記から判別できない。前者なら精度ではなく単なる一致度で、「精度は◯%落ちます」という⑦の言い切りの根拠にならない。後者なら、架空事業所のチェックリスト項目 × 対象3改定項目について**要更新/影響なしのゴールドラベルを人手で作る作業**が必要で、これがD7の内容にもG3/G4の確認手順にも入っていない。D7は「オフライン通し＋実測＋対比表UI＋デモ台本」で既に満載。
  - 加えてサンプル数が定義されていない。チェックリスト項目が10個なら判定は10件、一致率の刻みは10%単位になる。「精度が5%落ちます」という粒度の主張は**そもそも出せない**。審査員（特にmana氏・かずなり氏の層）に「何件で測ったんですか」と聞かれて「10件です」と答えると、⑤⑥⑦がまとめて薄くなる。
  - **②ビジネス成立性**: §8で②の実体欄は「ピッチ」のみ。G8が②に紐づいているが、G8は「キューが流れる」であって「誰が何にいくら払うか」ではない。「減算リスク・加算取りこぼし・監査指摘」を金額で語るとあるが、**具体的な円が設計書に一つもない**。価格設定も対象事業所規模も想定顧客の意思決定者もない。回遊審査で「これいくらで売るんですか」は必ず来る質問で、ここで詰まると②は5点中2点になる。均等配点なので、この1項目だけで総得点の7.5%。
  - **①課題の実在性**: 実体欄は「ピッチ／G2」。G2は根拠トレースであって課題実在性の証明ではない。「2ヶ月前の実改定への現場対応の実話」の**中身**（何人が何時間かけた、いつ気づいた、何を見落とした）が書かれていない。①は「一次情報で語れているか」が観点で、ソロで唯一取りに行ける5点なのに、設計書には抽象的な見出ししかない。
  - **工数**: §10のD1〜D8はすべて実装とリハで埋まっている。D8は「予備日 兼 通しリハ ＋ 成果物3点(a)(b)(c)」で、ピッチ資料（④の1枚・⑤の選定理由・⑥の原価対比・②の金額）を作る時間がゼロ。§8は8項目中5項目（①②④⑤⑧）の実体を「ピッチ」と書いているのに、**そのピッチを作る日が存在しない**。design.md 内部の矛盾。

- **提案**:
  - §6.3を「一致率」から**具体的な指標定義**に書き換える: 評価対象＝チェックリスト全項目 × 対象3改定項目の全ペア、正解＝人手ラベル、指標＝要更新の再現率と誤検知数の実数（率ではなく**実数**で出す。分母が小さいなら率を言わない方が誠実で、かつ突かれない）。
  - 正解ラベル作成をD2の副産物として組み込む。影響判定を実装しながら期待出力を書くので、追加コストは小さい。D7に持ち越すと確実に落ちる。
  - **②の金額をD1に前倒しする**。「後で決めるが最も高くつく」（§10の原則）はコードだけでなくピッチにも当てはまる。①の一次情報と②の金額は本人の頭の中にしかなく、実装で代替できない唯一の資産なので、疲弊した8日目に書かせない。
  - §10のD8を「予備日兼リハ」から分離し、ピッチ・数字の枠を明示的に確保する。撤退ライン（§4）に「D7終了時点でピッチの数字が埋まっていなければ、実装を止めてピッチに寄せる」を追加するのが均等配点への正しい防御。

### [C-4] 種別: 設計 / 深刻度: high

- **指摘**: G8とデモ台本#11の**「回線復帰」の検知方法と所要時間が未設計**で、加えて §5.2 の3部品以外に**オフラインで死にうる依存が残っている**（プリンタドライバの初回取得、フロントのCDN依存アセット、ローカル推論のサーマル劣化）。

- **破綻シナリオ**:
  - **復帰検知**: 台本#11は「回線を復帰 → 自動送信 → LINE着弾（手を触れない）」を**5秒**に割り当てている。実際に起きること:
    - Wi-Fi をONにしてから、AP再アソシエーション → DHCP → DNS → TLSハンドシェイク → LINE API 応答まで、混雑した会場APでは5秒では収束しない。
    - 会場Wi-Fiが**キャプティブポータル（認証ページ）**を挟む場合、再接続後にブラウザで認証をやり直す必要があり、「手を触れない」が原理的に破綻する。加えてポータル配下ではDNSが偽応答を返すため、単純な「pingが通ったらフラッシュ」の検知は**誤検知して送信失敗→retry_count増加**という最悪のデモになる。
    - フラッシュの**トリガ方式が設計にない**。ポーリングなら間隔が未定義（30秒間隔なら最大30秒待ち＝終幕が死ぬ）、OSの到達性コールバックなら実装が環境依存。§6.4に `retry_count` はあるが、リトライ間隔もバックオフも「何をもって復帰とみなすか」も書かれていない。
    - さらに §4 で「手動再送ボタンは作らない」と明記されているため、**フラッシュが発火しなかった場合の逃げ道が設計上ゼロ**。終幕でスタックしたら回復手段がない。
  - **プリンタドライバ**: USB直結プリンタをmacOSに初回接続すると、ドライバをネットワーク経由で取得しにいく挙動がある。D5の実装時にオンラインで繋いでいれば済むが、設計書にはプリンタ「調達」（D1）としか書かれておらず、**オフラインで印刷できる状態の確認がどのGにも入っていない**。G3の確認手順は「印刷排出が完走」だが、これをオフラインで検証するのはD7が初回。そこで初めて詰まると、③の本体（紙ループ）が丸ごと崩れる。
  - **フロントのアセット**: 承認UIをWebで作る場合、CDN配信のフォント（Google Fonts等）・アイコン・CSSを1本でも `<link>` で参照していると、Wi-Fi断で**レイアウトが崩れた画面**をブースで見せることになる。「オフラインでも動きます」の実演で画面が崩れるのは、機能が動いていても致命的に印象が悪い。自己ホストへの固定が設計に明記されていない。
  - **サーマル/電源**: 1台のラップトップで Ollama 8B ＋ ローカルASR ＋ 開発サーバ ＋ 印刷を同時に回す。回遊審査は数時間にわたり同じデモを何十回も繰り返すため、**後半ほどサーマルスロットリングで推論が遅くなる**。D7に測った実測値がブース後半では再現しない。また §5/G3 の「電源のみ」がAC給電を指すのかバッテリー駆動を指すのか文面から判別できず、ブースにAC電源が確保できるかも未確認（会場依存の前提）。バッテリー駆動なら省電力モードでGPU/CPUがさらに絞られる。

- **提案**:
  - **回線を会場Wi-Fiに依存させない**。専用のモバイルルータ or スマホテザリングを持ち込み、デモの「切断/復帰」は**アプリ内のネットワークスイッチ（またはルータの電源）**で行う。会場Wi-Fiの状態に終幕を預けない。これはキュー化の是非（R-16で決着済み）ではなく、その決定を当日成立させる条件の話。
  - 復帰検知を「LINE APIへの軽量ヘルスチェックを1秒間隔」に固定し、design.md に明記する。DNSやpingではなく**実エンドポイントの到達性**で判定する（キャプティブポータル誤検知の回避）。
  - 台本#11の秒数を実測で置き換える（C-2と同じ）。
  - 「手動再送ボタンを作らない」は仕様として維持しつつ、**デモ運営者だけが叩ける隠しフラッシュ（キーボードショートカット等）**を用意する。§7(a)の30秒復旧台本に載せる復旧手段であって、UIの仕様ではない。
  - §5.2の表に **プリンタドライバ・フロントアセット・電源** の3行を追加し、それぞれ「D1で解消」「自己ホスト固定」「AC前提／会場確認」と対応を書く。D5終了時点で**一度Wi-Fiを切って印刷してみる**チェックを入れる（D7が初回検証では遅い）。

### [C-5] 種別: 設計 / 深刻度: mid

- **指摘**: G6の「落ち」（デモ最大の山、③④⑧の3項目が乗る）が、**審査員が何を喋るか制御できない**うえに**LLMの非決定性**に無防備で、さらに「終了時刻欄が増えたのはチェックリスト更新の結果だ」という因果が画面上で見えない。

- **破綻シナリオ**:
  - 台本#2は「**日報を一言喋ってみてください**」と審査員に喋らせる設計。入力が完全に制御外になる。審査員が「今日は佐藤さんの家に行きました」とだけ喋った場合と、#6でまた別のことを喋った場合、2つの記録は**内容も構造も違う**。「終了時刻欄だけが新たに出現した」という比較が成立しない。
  - #6で審査員が「10時から11時まで訪問しました」と時刻を含めて喋ってしまうと、更新前のチェックリストでも時刻が記録に載る可能性があり、**落ちが落ちにならない**。
  - §6.5の `structure()` の実装がLLM任せの場合、同じ入力でも出力スキーマが揺れる。ブース本番の1回で「終了時刻」欄が出ないと、④（AI必然性）と⑧（次世代性）の実演根拠が同時に消える。G7のテキスト入力フォールバックはASR死亡への対策であって、この非決定性は救わない。
  - #6は10秒しかなく、「更新前の記録」と「更新後の記録」を**並べて見せる画面が設計にない**。審査員は#2の画面を10〜40秒前に見ただけで、記憶を頼りに差分を認識することになる。回遊中の審査員には無理。

- **提案**:
  - `structure()` のうち**チェックリスト照合部分を決定的処理にする**。`setChecklist` で受け取った項目名から**記録フォームの欄を機械的に生成**し、LLMは各欄の値を埋めるだけにする。こうすれば「チェックリストに終了時刻が入った → 欄が必ず現れる」が100%再現し、しかも §6.1 の「①はLLMを使わない」に続く**「LLMを使わない判断」の2例目**として⑤に加算できる。落ちの信頼性と審査点を同時に取れる。
  - 未入力欄を「**未入力（要確認）**」として明示的に表示する。審査員が時刻を喋らなくても欄が出るので、落ちが入力内容に依存しなくなる。むしろ「新しいルールで必要になった項目が、埋まっていないと分かる」方が現場価値の説明として強い。
  - 台本#6を「**Before/Afterの記録を左右に並べ、増えた欄をハイライト**」に変える。#5で紙2枚を見比べさせるのと同じ構造をデジタル側でも作る。
  - 審査員に喋らせるのは維持しつつ（体験価値が高い）、**定型の例文カードをブースに置く**（「10時に伺って、清拭と血圧測定をしました」）。入力の自由度を演出として残しながら、実質は制御された文になる。
