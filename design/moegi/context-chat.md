## ブロック1: 決定事項サマリー（初期検討の帰結）

### プロダクト
**通達Diff→現場手順自動更新エージェント（訪問看護向け）**

厚労省等の通達PDF新旧版を入力 → 変更点抽出 → 事業所固有の手順書・チェックリスト・算定条件への影響判定 → 更新案生成 → 管理者承認 → 現場が使い慣れた媒体（紙・LINE・FAX形式）で配布。

### ハッカソン文脈
- AI HACK 2026（8/8〜8/16、発表8/16、賞金総額100万円）
- テーマ「本番で通用する次世代のAIプロダクトを作る」
- 審査員4名 = ちょまど（MS Developer Advocate）／かずなり（生成AIインフルエンサー）／mana（MAKEAI CEO・中小企業AI実装）／みやび（スモビジAIマーケター）
- チーム上限3名

### ポジショニング
- 競合の算定エージェント各社は**請求レイヤー**。本プロダクトは請求の手前の**運用レイヤー**（現場の手順書・チェックリスト）を張る
- 低リテラシー業界を前提にした「**AIを使わせないAI**」設計。現場に新UIを覚えさせず、入口も出口も既存媒体
- 仮ワンライナー: 「現場は何も覚えなくていい。ルールが変わったら、いつもの紙が新しくなって届くだけ」
- 決裁者向けの言語は**金額**（減算リスク・加算取りこぼし・監査指摘）、現場向けは**学習コストゼロ**

### テーマ「本番」への回答3点
1. 既存媒体による定着設計
2. 人間承認フロー ＋ 変更根拠の通達原文トレース
3. 円換算で語る購買設計

「次世代」の主張 = **業務に溶けて見えなくなるAI**。

### 必須要件（本人指定）
LLMをローカルLLMに切り替え可能なアーキテクチャにする。**精度低下は許容**。
→ LLM呼び出しを抽象化レイヤーで分離し、工程ごとにクラウド/ローカルをルーティングできる形。
機微情報をクラウドに出せない事業所にも売れる、という「本番で通用する」主張の一部としてピッチにも使う。

### 9日間スコープ（固定）
実在の通達1改定ペア ＋ サンプル事業所1件分の手順書。
パイプラインは「diff抽出 → 影響判定 → 更新案 → 承認 → 配布形式出力」の一本道。
**複数事業所対応・汎用化はやらない。**

## ブロック2: 審査基準確定後の変更点（追記）

### 正式審査基準（運営公式で裏取り済み）
**8項目 × 5点 = 40点。配点は均等**（重みづけの偏りなし＝ユーザー確認済み）。

| # | 項目 | 観点 |
|---|---|---|
| ① | 課題の実在性 | 一次情報で語れているか |
| ② | ビジネス成立性 | 誰が何にいくら払うか |
| ③ | 完成度・デモ | 触れて数十秒で価値がわかる |
| ④ | AIである必然性 | AIでなければならない体験か |
| ⑤ | 技術的な作り込み | 構成の妥当性・精度の改善 |
| ⑥ | LLMコスト | 実測原価の提示と削減施策 |
| ⑦ | セキュリティ | 機密データを預けられるか |
| ⑧ | 次世代性・独創性 | 1年前には作れなかった体験 |

審査形式: **展示ブース回遊形式**（審査員がブースを回る）。

> 注: 審査基準を最初に知ったスクリーンショットは orcarouter.ai のスポンサースライド（フッターと「⑥⑦の2項目から攻略しましょう」の営業コピー付き）だった。⑥⑦の強調はスポンサー文脈込み。配点構造自体は参加者向け要項で裏取り済みで、**均等配点が確定**。
> 戦略上の含意: ⑥⑦に全振りせず、8項目を満遍なく5点狙いに行く。ORCAスライドに乗って⑥⑦へ偏重したチームは10点分を厚くして30点分を薄くすることになる。

### スコープ変更
- 既存の「口頭 → 日報 → 月報」資産を**接続に限定して**統合
- 接続点は「**更新済みチェックリスト → 日報エージェントの参照**」の**一箇所のみ**。日報側は移植のみ、改修しない
- ブースデモは「日報を喋る → 通達変更 → チェックリスト更新 → 日報に新項目が反映」の**30秒ループ**
- 意図: 見栄えではなく③「触れて数十秒で価値がわかる」の弱点を埋めるため（通達処理単体はバッチ的でブースで触らせる瞬間がなかった）
- 副次効果: 通達Diff → 手順書 → 日報 → 月報（加算エビデンス）で「規制 → 運用 → 記録 → 請求根拠」のループが閉じ、②も強くなる

### 実装スコープ外
**VLM（手すり設置・導線管理）は実装しない。** ロードマップスライドの1行に留め、実装には1秒も使わない。
理由: コア価値（ルール変更への追従）との接続が薄く、「結局何のプロダクト？」と焦点をぼかす。

### ORCA ROUTER
- **組み込みマスト**（運営/スポンサー要件）。参加者全員が使うため、⑥の勝負ポイントは「使ってるか」ではなく「**使いこなしてるか**」
- 差が付く2点:
  1. **工程別ルーティング**（diff抽出は安価モデル、影響判定だけ高精度モデル）に**選定理由**を付けて⑤にも効かせる
  2. **通達1本あたり・日報1件あたりの実測原価**をデモ画面に常時表示
- ORCA ROUTER の分析画面がコスト実測の証拠に使えるなら、⑥用の資料が半分タダで手に入る

### 設計上の注意（ローカルLLM切替との相性）
ORCA ROUTER がセルフホスト/ローカルのエンドポイントにルーティングできるか未確認。
- できる → 全部ゲートウェイ経由で一本化
- できない（クラウドのみ）→ **パイプラインを ORCA の SDK に直結させず、自前の薄いアダプタを一枚挟んで「クラウド工程 → ORCA、機微工程 → ローカル直」と分岐**

**採用方針: どちらに転んでも壊れないよう、自前アダプタを挟む構成を前提として design.md を書く。**
効果: 「機微データはゲートウェイにすら出ません」が⑦の追加の一文になり、マスト要件も同時に満たせる。

### デモの故障モード対策
会場騒音で音声認識が死ぬリスクが高い（過去のローカルLLMハッカソン展示でマイク周りは事故った実績）。
→ **指向性マイク**、および**音声が死んだ時のテキスト入力フォールバック**をデモ設計に最初から入れる。

## ブロック3: /idea-review レビュー5指摘の取捨選択（確定）

### ④ AI必然性への回答 → **採用、最優先**
一度も言語化していなかった痛点。回答の型:

> 規制のdiff自体はルールベースで取れる。LLMが必須なのはその先——**通達の曖昧な行政文書表現と、事業所ごとに書き方がバラバラな手順書との間の非構造マッピング**。「別表第7に掲げる者」という通達文が、A事業所の手順書では「医療依存度の高い利用者」、B事業所では疾患名の列挙になっている。この表記揺れの橋渡しは**1年前のモデルでは精度が出なかった**。

最後の一文は⑧（1年前には作れなかった体験）にも同時に効く。**ピッチに1枚入れる。**

### ORCAフォールバックのデモ化 → **採用（「これは宝」）**
全チームがORCAマストで同じ障害リスクを抱える中、
「ブースで**意図的にゲートウェイを切断** → 機微工程がローカルLLMに即時フェイルオーバー → **精度は落ちるが業務は止まらない**」を見せる。
⑥⑦⑧を一撃で取る演出。元々の必須要件を使うだけで実装追加コストがほぼゼロ。
**デモ台本の後半に固定で入れる。**

### 配布が見えない問題 → **採用、ただしFAXは紙芝居でいい**
- **LINE通知は実物を1本通す**（Messaging API で1日仕事）
- FAXは実回線を引くのは無駄。**ブースに小型プリンタを置いて、更新済みチェックリストがその場で印刷されて出てくる**
- 審査員に紙を手渡せる ——「現場に届くのはこれです」
- 展示回遊形式で**唯一の物理的な持ち帰り物**になり、「AIを使わせないAI」が文字通り手に取れる

### データ出所 → **架空一択**
- Momonga のクライアント実データはブースに出した瞬間⑦の説明と自己矛盾する
- **厚労省の公開標準様式＋運営規程テンプレから架空事業所「◯◯訪問看護ステーション」を組む**
- 「公開様式ベースの架空データです、実運用では事業所内で完結します」と言えるようにする
- これ自体がセキュリティ設計の説明になる

### 体制・実装順 → **承認UIを後回しにしない、に同意**
順序案:

| 日 | 内容 |
|---|---|
| D1-2 | パイプライン一本道（diff → 影響判定 → 更新案）＋ 自前アダプタ（ORCA/ローカル分岐） |
| D3-4 | 承認UI ＋ 原文トレース |
| D5 | 日報接続（移植のみ） |
| D6 | 配布（LINE実物 ＋ 印刷） |
| D7 | コスト実測表示 ＋ デモ台本 |
| D8 | 予備日 兼 リハーサル |

チーム合流するなら、**D6-7の工程とブース造作がそのまま渡せる仕事**になる。

## ブロック4: チーム編成に関する方針

チームに組み込まれそうな気配あり。方針:

- ブレる原因は「ドメインが違う人が集まる」ことではなく「**プロダクトの意思決定を合議にする**」こと
- ①課題の実在性は5点丸ごと本人の現場知識にしか担保できない
- **合流条件は一つ: 「アイデアとドメイン判断のオーナーは自分」を最初に口に出して合意する**
- 曖昧なまま「みんなでアイデア出しから」になったら、行き着く先は誰のドメインでもない汎用プロダクトで①②が沈む。それなら断ってソロの方がいい
- チームの価値は「アイデアを混ぜること」ではなく「**ドメイン非依存の工程を渡せること**」——フロントの磨き込み、⑥用コスト計測ダッシュボード、ピッチスライドのデザイン、当日の呼び込み
- 違うドメインの人は「業界を知らない審査員に伝わるか」のテスターとしても機能する
- **判断基準: 相手が「その課題、面白いから乗りたい」なら組む。「俺のアイデアも混ぜよう」なら断る**
- design.md を唯一の真実にする /design-loop 運用が、そのままチーム統制の道具になる（「設計はこのファイル、疑問は台帳へ、ドメインの前提には触らない」）
