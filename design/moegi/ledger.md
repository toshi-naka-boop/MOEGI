### N-7: デモのアンカーが新規項目として提案されない（**解決・v11**）
- 種別: **設計**（v11 / §6.5・§7）
- 内容: `--label c --single-shot` の実測で、影響判定6件は**すべて既存項目の「要更新」**であり、
  **新規項目「評価の記録」の提案（`sitedoc_item_id = null`）が1件も出ていない**。
  原因は `match_requirements` の規則——**既存項目が1つでも「要更新」になると新規項目の要否を問わない**
  （`matched_existing` で早期 continue）。ローカル8Bが過剰に「要更新」を返すため、
  この規則が毎回アンカーを潰す。しかも過剰検出の内容自体が的外れ
  （「バイタルサインの記録」「訪問日数・訪問頻度の記録」まで要更新にしている）。
- 破綻シナリオ: **デモの落ちが出ない。** §7 台本 #4 は「チェックリストに『評価』欄を追加する更新案」が
  画面に立つことが前提で、G6・G9 の合格条件もそこに乗っている。
  現状の実装は「無関係な既存6項目を書き換えろ」と提案する画面になる。
- 処置（**ユーザー決定・2026-08-09**）: **完全新設の条文（`Change.kind == "追加"`）は、新規項目の提案を必ず作る。**
  - 「新規項目の要否を常に問う」案は**却下**——呼び出しが増える割に、提案が出るかどうかは
    LLMの `needed` 判定に依存したまま。**LLM依存を消すことが目的**なので、条文の種別で決め打ちする
  - `needed` 判定を無視するので、LLMが根拠引用を返さない／幻覚を返した場合は
    **条文冒頭を根拠に据える**（新設された条文そのものが根拠なので捏造にならない）
  - **timeout でも提案を作る**（応答を必要としないため）。回線断のデモで落ちが消えない
  - トレードオフ: **判定の一部をルールに固定する**。allowlist の `old_path` が空である
    ＝完全新設であるという D1 の判断が、そのまま提案の有無を決めることになる
- 実測（2026-08-09・`--label c`・単発）: 更新案 **6件 → 7件**。うち1件が新規項目の提案で、
  根拠は通達原文中に実在する引用（★アンカーが画面に立つ）
- 副産物: 過剰検出そのものは残る → **N-8 として分離**
- 状態: **design.md v11 に反映済み**
