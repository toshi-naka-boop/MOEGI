# MOEGI UI/UX デザイン依頼ブリーフ（Claude Design へそのまま渡す用）

> このファイルはデザイン依頼のための資料。実装側の制約を先に固定してあるので、
> ここに書いていないライブラリ・手法は使えないと考えてほしい。

---

## 0. これは何のアプリか

**訪問看護事業所向けの業務ツール**です。2年に1度の診療報酬改定で厚労省の通達が変わったとき、
「うちのチェックリストのどこを直せばいいか」を提示し、承認された変更が現場の記録画面まで
届くようにします。看護師が訪問記録（日報・SOAP）を音声で残し、1ヶ月分が月報に積み上がります。

**使う人は2種類あり、デバイスが違います。**

| 誰 | どこで | 何をする |
|---|---|---|
| 管理者・事務 | PC（デスク） | 更新案の承認/却下/編集、月報の確認、配信キューの確認 |
| 看護師 | **スマホ・タブレット**（訪問先の車内など） | 日報の録音・入力、結果の確認 |

さらに **ハッカソンのブースで審査員に75秒で見せる**という用途があります。画面が「何が起きたか」を
一目で伝えられることが重要です。

## 1. 絶対制約（これを外すと実装できません）

| # | 制約 | 理由 |
|---|---|---|
| 1 | **外部CDNを一切使えない**。Webフォント・アイコンフォント・外部CSS・外部JSすべて禁止 | 会場のWi-Fiを切ってもデモが完走することが必須要件（オフライン完走）。1つでも外部参照があると落ちる |
| 2 | **ビルド工程なし**。React / Vue / Tailwind / SCSS / PostCSS すべて使えない | Pythonの文字列としてHTMLを組み立てるサーバーレンダリング構成。npmもnode_modulesも無い |
| 3 | **素のHTML + 素のCSS + 素のJS のみ** | 上と同じ。CSSは1つの `<style>` に収まる形で書いてほしい |
| 4 | **SPAではない**。すべて `<form>` のPOST → 303リダイレクト → フルページ再読み込み | 状態はサーバー（SQLite）が持つ。クライアント側ルーティング・状態管理は無い |
| 5 | **画像アセットを置けない**。ロゴ画像・アイコンPNG/SVGファイルは不可 | 使えるのは**絵文字**と**HTMLに直接書いたインラインSVG**だけ |
| 6 | **フォントはOS標準のみ** | 現在の指定: `-apple-system, "Hiragino Sans", "Yu Gothic", sans-serif` |
| 7 | **日本語UI**。文章量が英語より多くなる前提でレイアウトしてほしい | |

**つまり**: 「Tailwindのクラス名で書かれたデザイン」「Figmaの画像アセット前提のデザイン」
「shadcn/ui などのコンポーネントライブラリ前提のデザイン」は**そのままでは実装できません**。

## 2. 使ってほしいデザイントークン（既存・変更提案は歓迎）

「萌黄（もえぎ）」＝黄緑がブランドカラーです。紙と若葉のイメージで、
医療系にありがちな青ではなく**和のやわらかい配色**にしています。この方向性は維持したいです。

```css
:root {
  --ink: #1c1f1a;              /* 本文 */
  --ink-soft: #565f4f;         /* 補助テキスト */
  --paper: #fbfaf5;            /* 背景（生成りの紙） */
  --paper-raised: #ffffff;     /* カード面 */
  --line: #dde0d2;             /* 罫線 */
  --moegi: #7a9c2e;            /* ブランド・主ボタン */
  --moegi-soft: #eef3e1;       /* 淡い面 */
  --moegi-deep: #55701f;       /* リンク・ホバー */
  --warn: #a8641b;             /* 注意 */
  --warn-soft: #fbf1e2;
  --danger: #a8391f;           /* 危険・停止 */
  --status-approved: #3f7d3a;  --status-approved-bg: #eef6ea;
  --status-rejected: #7a7f70;  --status-rejected-bg: #f1f1ec;
  --status-edited:   #3a5f8a;  --status-edited-bg:   #eaf1f8;
}
```

**ダークモード対応は必須**です（`prefers-color-scheme: dark` で同じトークン名を上書きする方式。
既にダーク値も定義済み）。色を追加する場合は、必ずライト/ダーク両方の値をください。

## 3. レスポンシブ・操作の要件

- 本文カラム幅は現在 `max-width: 880px`
- ブレークポイントは `600px` を1つだけ使用中（それ以上増やしたくない）
- **スマホでのタップ対象は最低44px**（処置ボタン、録音ボタンは48px）
- 看護師は**片手・屋外・手袋の可能性あり**。タップ対象は大きく、間隔を空けたい
- 横スクロールを発生させない。表は縦に積むか、その要素だけ横スクロールさせる

## 4. 画面インベントリ（9画面）

デザインしてほしい画面と、それぞれが持つ状態です。

### ① ホーム `/`
- 新しい分析を実行するフォーム（対象条文のプルダウン＋実行ボタン）
- 過去の実行一覧
- 各機能への導線（日報、月報、監査記録、配信キュー）
- **空状態あり**（まだ分析結果がない）

### ② 更新案の承認 `/runs/{id}` ★最重要
このアプリの中心です。1件ずつカードで並びます。カード1枚が持つもの:
- 対象の条文ラベルと変更種別（改正／追加）、対象のチェックリスト項目名
- **判定チップ**（要更新／判定不能）と**ステータスチップ**（未承認／承認／却下／編集済）
- 信頼度の数値
- 判定理由の文章
- **Before / After の2カラム比較**（変更前の項目文言 → 変更後）
- **原文トレース**（開閉式。旧版と新版の条文本文を並べ、根拠になった一文をハイライト）
- 操作: 承認 / 却下 / 文言を編集して保存（テキストエリア）
- ページ下部: FAXプレビューPDF生成、配信履歴

**状態**: 未承認 / 承認 / 却下（薄く表示）/ 編集済 の4状態で見た目が変わります。

### ③ Before/After 比較 `/runs/{id}/before-after`
- 変更前と変更後のチェックリストを左右に並べ、追加・変更された項目をハイライト
- 同じ発話を両方のチェックリストで構造化した結果を左右に並べる
- 「入力音声は同一。差はチェックリストのみ」という但し書きを目立たせたい（これが証拠になる）

### ④ 日報の入力 `/nippou` ★スマホ最優先
- 利用者コードの選択、訪問日
- **処置内容のボタン（10個・複数選択）** — 現在はピル型のトグル
- **録音ボタン**（録音中は見た目が変わる）＋録音状態のテキスト
- またはテキスト直接入力（テキストエリア）
- 出力形式の選択（日報は常に作成／SOAPも作るかのチェック）
- 上部に注意書きが2つ（ローカル処理である旨、Privacy Gateを通す旨）

### ⑤ 日報の結果 `/nippou/structure`
- **Privacy Gate のサマリカード**（後述の4状態）
- 保存した旨のメッセージ
- 仮名化済みの発話内容
- 日報テーブル（チェックリスト項目 × 記入済み/未記入 × 抜き出した値）
- 評価（看護目標・達成度・効果）
- SOAP（S/O/A/P の4区分）

### ⑥ セキュリティ検査で停止した画面（⑤の別状態）
- 停止した理由（日本語の箇条書き）
- **修正して再検査**するテキストエリア＋ボタン
- ここが**デモの見せ場**なので、「止まった」ことが強く伝わる見た目にしたい

### ⑦ 月報 `/monthly`
- 利用者コードと対象月を選ぶフォーム
- サマリチップ（訪問◯回・訪問日数◯日・評価の記入◯/◯）
- 処置別の実施回数（表）
- チェックリスト項目の記入率（表・割合の可視化があると良い）
- **バイタルの推移**（日付 × 血圧/体温/脈拍/SpO2 の表。グラフにするなら**インラインSVGのみ**）
- 注意書き（読み取れなかった訪問の件数など）
- **空状態あり**（その月の日報が無い）

### ⑧ 配信キュー `/deliveries`
- 「送信待ち n件」の強調表示
- 各配信の状態（送信待ち／送信済み）、宛先、試行回数、送信時刻
- **手動の再送ボタンは絶対に置かない**（設計上の決定。押さないと届かないなら意味が無いため）
- **空状態あり**

### ⑨ 仮名化処理の監査記録 `/privacy/audits`
- 1件ごとに: 日時、Gate状態、検出した種別と件数、処理時間、構造化へ進んだか、外部送信の有無
- **空状態あり**

### 全画面共通
- 上部に「← MOEGI ホーム」のナビ
- **送信待ちがあるときだけ**出る通知バー（📮 送信待ち n件）

## 5. 重要な状態表現

### Privacy Gate の4状態（⑤⑥で使う）
| 状態 | 意味 | 見た目の要求 |
|---|---|---|
| `passed` | 検査通過。日報を作ってよい | 落ち着いた肯定。**過度に「安全です」と見せない** |
| `review_required` | 個人を特定し得る情報が残っている可能性 | 注意。人の確認を促す |
| `blocked` | 記録に残せない情報を検出（保険証番号など） | **強い停止**。処理が止まったことが明白に |
| `failed` | 検査自体が完了しなかった | 停止と同等 |

### 待ち時間が長い操作がある（重要）
- 更新案の生成: **約47秒**
- 日報の構造化: 3〜30秒
- 現在は「ボタンを無効化して『実行中…』に変える」だけです。**固まって見える**ので、
  進行が伝わる表現がほしい（ただしアニメーションは軽量に。CSSのみで）

## 6. 文言・表示のルール（法務・プライバシー上の制約）

デザイン内のダミーテキストもこれに従ってください。

**禁止**:
- 「匿名化済み」「個人情報ではありません」「完全に安全」「完全匿名」— **使用禁止**
  （実際には直接識別子を仮名化しただけで、病状・服薬などは残るため。テストで機械的に検査しています）
- 実在の人名・住所・電話番号・事業所名をダミーデータに使うこと

**正しい言い方**: 「直接識別子を仮名化しました。仮名化後も病状・服薬などの要配慮個人情報は残ります」

**表示してはいけないもの**:
- 患者・職員の**実名**（画面には仮名 `PATIENT_001` `NURSE_001` `長女` のみ）
- 検出した個人情報の**値そのもの**（出すのは「電話番号 1件」のような**種別と件数**だけ）

**ダミーデータはこれを使ってください**:
- 利用者コード: `P-100234`
- 仮名: `PATIENT_001`, `NURSE_001`, `DOCTOR_001`, `FACILITY_001`, `長女`
- タグ: `[[PHONE]]`, `[[ADDRESS]]`, `[[EMAIL]]`
- チェックリスト項目例: 「バイタルサインの記録」「訪問日数・訪問頻度の記録」「特記事項」
- 処置例: 「創傷処置（褥瘡ケア等）」「吸引」「点滴・注射」「バイタル測定」

## 7. 成果物の形（実装しやすい形でお願いします）

**理想**: 画面ごとの**単一HTMLファイル**（`<style>` を1つ含む静的モック）。
- CSSは**カスタムプロパティ（上記トークン名）を使って**書いてください
- クラス名は既存のものを流用できると差分が小さくて助かります:
  `proposal` `chip` `chips` `meta` `diff` `before` `after` `field-label` `actions`
  `edit-form` `run-warning` `run-list` `run-form` `trace-text` `rationale`
  `procedure-buttons` `procedure-pill` `record-controls` `home-nav` `confidence`
- 新規クラスを足すのは歓迎です（命名だけ揃えてもらえれば）

**避けてほしい形**:
- Tailwind等のユーティリティクラスで書かれたHTML
- 画像ファイル前提のデザイン（アイコンは絵文字かインラインSVGで）
- Figmaのスクリーンショットだけ（実装時に色・余白の値を推測することになるため）

**優先順位**（時間が限られる場合はこの順で）:
1. ② 更新案の承認（アプリの中心・デモの主役）
2. ④ 日報の入力（スマホ最優先）
3. ⑤⑥ 日報の結果 と 停止画面（デモの見せ場）
4. ⑦ 月報
5. ① ホーム
6. ③⑧⑨

## 8. 参考: 現在の実装

- UIは `src/moegi/webapp.py` の1ファイル。CSSは `_PAGE_STYLE` という文字列定数、
  HTMLはPythonのf-stringで組み立て
- 現在のクラスとトークンは §2・§7 に列挙したものが全部

  **HTML構造を大きく変える提案には、その理由を添えてもらえると判断しやすいです**
