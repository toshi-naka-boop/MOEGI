# 記事ドラフト: 訪問看護の「通達 → 現場手順 → 記録」を、LLMに任せすぎずに繋いだ話

> **これは公開用記事のドラフト。** 事実・数値はすべてリポジトリの実測に基づく。
> 公開前チェック: ①実クライアントデータ・実在の氏名が1つも出ていないか ②数値の出典（ledger ID）が
> 追えるか ③「完全に安全」「匿名化済み」といった過大な表現が無いか。

---

## 何を作ったか

訪問看護の事業所には、2年に1度の診療報酬改定のたびに「**通達は読んだ。で、うちのチェックリストの
どこを直せばいいのか**」という作業が降ってくる。厚労省の通知は数百ページあり、変わったのは
その中の数行で、しかも現場のチェックリスト項目とは**まったく違う言葉で書かれている**。

MOEGI はここを繋ぐ。

```
通達の新旧PDF
   → ②差分抽出 → ③-a 要件抽出 → ③-b 突合 → ④更新案生成
   → 人が承認 → チェックリストが更新される
   → 訪問記録（日報・SOAP）がその新しいチェックリストで構造化される
   → 1ヶ月分が月報として積み上がる
```

面白いのは末端で、**「評価の記録」という項目が新設されると、その月から日報の入力欄に
「目標に対する評価は？」が現れる**。制度の変更が、現場が実際に打ち込む画面まで到達する。

---

## この記事で書きたいこと

うまくいった機能の紹介ではなく、**LLMに任せる範囲をどこで切ったか**の話をしたい。
開発中に何度も同じ形の失敗をして、そのたびに境界を引き直した。結果として残ったのは
「LLMは**候補を出す**が、**正しさは決定論的なコードが保証する**」という、わりと退屈な原則だった。

---

## 失敗1: LLMに「根拠の逐語引用」を書かせた

更新案には「通達のどの文が根拠か」を必ず付ける設計にしていた。最初の実装は、LLMに
根拠の文をそのまま書き写させていた。

**壊れた。** 引用が途中で切れる、微妙に言い換わる、存在しない文が生成される。
再現率は 0.0% まで落ちた。原文トレース画面は「原文にハイライトが当たらない」状態になった。

**直し方**: 判定と再現を分離した。条文を句点で機械的に分割し、`S1`, `S2`… とIDを振る。
LLMには**IDだけを返させる**。引用文字列はコード側が `segments` から切り出す。

```python
# LLMが返すのは "evidence_segment_id": "S2" だけ。
# 引用文字列は常にコード側の文分割結果から取り出す。
def _verified_evidence(entry, change, segments):
    seg_id = str(entry.get("evidence_segment_id") or "").strip()
    for segment in segments:
        if segment.id == seg_id:
            return [Evidence(quote=segment.text.strip(), offset=segment.offset, ...)]
    return None   # 実在しないIDなら根拠不成立 → 更新案を作らない
```

再現率 0.0% → 33.3%。それ以上に大きいのは、**「引用が崩れる」という失敗モードが
原理的に起こらなくなった**ことだ。LLMが選べるのは「どの文か」だけで、「何と書いてあるか」は
選べない。

## 失敗2: 処置名をLLMに抽出させようとした

日報で「今日はどんな処置をしたか」を記録する。発話から抽出させようとして、やめた。

「褥瘡処置」「じょくそう処置」「創傷処置」——音声認識の揺れとLLMの言い換えが二重に乗ると、
同じ処置が3通りの名前でDBに入る。**月次で集計した瞬間に破綻する。**

**直し方**: 10項目固定のボタン選択にして、選ばれた文字列を**LLMを1回も通さずに**格納した。

```python
# procedures は LLM に通さず、そのまま NippouRecord へ入れる
record = agent.structure(text, procedures=procedures)
```

つまらない結論だが、**語彙が閉じているものを自由文で扱う理由はない**。

---

## 失敗3: プロンプトを「良くなった気がする」で評価していた

突合（通達の要求 × チェックリスト項目）の精度が上がらなかった。プロンプトを書き換えては
1〜2件試して「よくなった気がする」を繰り返していた。

**直し方**: 本番コードをそのまま呼ぶ評価ハーネスを書き、48セルのゴールドセットで測った。

| 版 | 正解 | 率 |
|---|---|---|
| 改訂前 | 35/48 | 72.9% |
| 1巡目 | 43/48 | 89.6% |
| 2巡目 | 45/48 | 93.8% |

ここで効いたのは**プロンプトに「実際に間違えた例」を書く**ことだった。抽象的な指示
（「無理に要更新にしないこと」）はほとんど効かず、実測で出た誤検出2件をそのまま
反例として貼ったら一気に改善した。

さらに、複数のモデルベンダー（Claude と GPT系）に**同じプロンプトを批評させた**。
自分のモデルに自分のプロンプトを評価させると甘くなる。別ベンダーの指摘は容赦がない。

## 失敗4: セキュリティ層を「LLMに仮名化させる」で作りかけた

ハッカソンでセキュリティが重視されると分かり、訪問記録の仮名化層を後から足した。
最初の設計は「ローカルLLMに個人情報を消してもらう」だった。

**これは失敗3と同じ形の間違いだった。** LLMの出力が正しいことを、誰も検証していない。

**直し方**: 4層に分けた。

```
①ルール検出（決定論的）     電話・住所・生年月日・保険証番号・APIキー…
②ローカル辞書（決定論的）   事業所マスタの氏名・施設名・住所・電話
③ローカルLLM（補完のみ）    「娘の花子」のような文脈依存の固有名だけ
④再検査（①②と同じ検出器）  ③から完全に独立。残っていたら通さない
```

肝は④で、**③が「消したつもりで消せていない」を、③を使わずに検知する**。
そして④が落ちたら fail-closed——人が確認するまで日報生成へ進まない。

もうひとつ効いたのが、**「そもそもLLMに患者を同定させない」**という判断だ。
月報は「同じ人の1ヶ月分」をまとめる必要があるが、その同一性判定をLLMに委ねると
検証できない。訪問記録時に利用者コードを**選択式**で確定させ、そこから鍵つきHMACで
安定した仮名を導出することにした。

```python
def stable_pseudonym(code, *, prefix="PATIENT", key_path=DEFAULT_KEY_PATH):
    key = _load_or_create_key(key_path)
    digest = hmac.new(key, f"{prefix}:{code}".encode(), hashlib.sha256).hexdigest()
    return f"{prefix}_{digest[:12]}"
```

鍵つきにしたのは、利用者コードが桁数の少ない値だからだ。素のSHA256だと総当たりで逆引きできる。

## 失敗5: 実機で動かすまで、一番危ない失敗に気づかなかった

仮名化層のテストは100件書いた。全部フェイクのLLMで通していた。

デモ収録の直前に、**実機のOllamaで3モデル走らせて**みた。そこで7Bクラスのモデルが
とんでもないことをした。

```
入力: 「…ロキソニン60mgを内服中。膝の痛みは軽減。特変なし。」
出力: 「PATIENT_001さんは昨日から発熱があります。長女から連絡がありました。」
```

**プロンプトに書いた出力例を、そのまま本文として返してきた。** 仮名化ではなく、
まるごと別の文への差し替えだ。看護記録としては最悪の壊れ方（服薬情報が消えて、
起きていない発熱が記録される）。

このとき「入出力の文字数比が閾値を超えたら止める」というガードは既に入れていたが、
**長さが近かったので発火しなかった**。危うく通過するところだった。

**直し方**: 数値の保存を決定論的に検査するガードを足した。バイタルも用量も回数も数字なので、
入力にあった数字が出力から消えていたら、それは臨床情報の欠落だ。

```python
def _dropped_clinical_numbers(before: str, after: str) -> list[str]:
    """仮名（PATIENT_001）とタグ（[[PHONE]]）の数字は除いてから比較する"""
    remaining = list(_clinical_numbers(after))
    dropped = []
    for number in _clinical_numbers(before):
        if number in remaining:
            remaining.remove(number)
        else:
            dropped.append(number)
    return dropped
```

再実行すると、同じ入力が `clinical_numbers_dropped` で確実に止まるようになった。

**教訓**: モックのテストは「書いたロジックが動くこと」しか証明しない。
**実機のモデルが何をしでかすか**は、実機で回さないと分からない。

## 結果として残った原則

1. **LLMには「選ばせる」。「書かせる」のは検証できる範囲だけ。**
   文IDを選ばせる。項目番号を選ばせる。文字列を書き写させない。
2. **語彙が閉じているものは選択式UIにする。** 処置名、利用者コード。
3. **LLMの出力は、LLMを使わない検査で確かめる。** 独立した再検査、数値の保存チェック。
4. **迷ったら止める（fail-closed）。** タイムアウト・スキーマ違反・接続失敗・残存リスク超過——
   全部「人が確認する」に倒す。安全側に倒れた回数は監査記録に残るので、後から緩められる。
5. **精度は測ってから語る。** ゴールドセットが無い改善は改善ではない。

## 今後の課題と、その改善スキーム

ここからは**まだ解けていない**部分と、どう解くつもりかを書く。

### 課題1: 「同じ項目」の同一性が保証されていない

チェックリスト項目の識別子が**ラベル文字列そのもの**（可変な自然キー）になっている。
更新案が承認されてラベルが変わると、過去の判定結果・ゴールドセットの正解表・
月報の集計キーが指す先を失う。

**改善スキーム**: 項目に不変IDを導入する。ただし波及範囲（設定ファイル・DBスキーマ・
評価データ）が大きいので、**「壊れたら気づける」を先に入れる**。現状は、適用できなかった
更新案を `unmatched` として画面に出すところまで実装した。**静かに消えるのを、
見えて止まるに変える**のが先で、IDの導入はその次。

### 課題2: LLMの見落としは、再検査でも捕まらない

再検査はルールと辞書に載っているものしか検知できない。辞書に無い固有名をLLMが
見落とし、かつ `residual_risk: low` と自己申告した場合、そのまま通る。

**改善スキーム**: 仮名化にもゴールドセットを作る（失敗3で有効だったやり方をそのまま持ち込む）。
「この発話にはこの識別子が含まれる」という正解表を合成データで作り、再現率を測る。
測れるようになって初めて、モデル変更やプロンプト改訂の良し悪しが判断できる。

### 課題3: 属性の組み合わせによる再特定は消せない

「80代・独居・胃瘻」だけで、利用者の少ない事業所では個人が絞れる。これは仮名化では
原理的に消せない。

**改善スキーム**: 消すのではなく**明示する**。UIとドキュメントで「直接識別子を仮名化した」
としか書かない。「匿名化済み」「個人情報ではない」と書かないことをテストで固定した。

```python
def test_source_and_docs_avoid_overclaiming_wording(self):
    FORBIDDEN = ("匿名化済み", "個人情報ではない", "完全に安全", "完全匿名")
```

限界を書き落とさないことを、CIで守る対象にする。

### 課題4: 認証・認可がまだ無い

現状アプリに認証が無い。実名を画面に出す経路を作らないことで最悪ケースは避けているが、
実運用には**ユーザー認証とロールベースの認可**（仮名対応表の復号権限、Privacy Gateの
モード変更権限、監査記録の閲覧権限）が要る。

**改善スキーム**: 権限が要る操作を**先に、権限が無くても壊れない形で作っておく**。
仮名対応表の復号関数は実装済みだが、Webからは1箇所も呼んでいない。認証を足すとき、
「呼び出し箇所を探して権限チェックを入れる」ではなく「呼び出し箇所を作る」側から始められる。

### 課題5: マスタ連携がまだ合成データ

仮名化辞書は完全な架空データ。実運用では電子カルテ・人事システムとの同期が要る。

**改善スキーム**: **その同期経路自体が新しい外部通信になる**ことを設計の前提に置く。
今は「辞書の内容を外部にもローカルLLMにも渡さない」ことをテストで固定してあるので、
同期を足すときにこの不変条件が壊れれば、テストが落ちて気づける。

---

## まとめ

やったことの大半は「LLMにやらせない範囲を決める」作業だった。

LLMが強いのは、**行政文書の言い回しと現場文書の言い回しを、意味のレベルで結びつける**ところ。
これは1年前は精度が出なかった処理で、ここだけはLLMでないと解けない。

一方で、引用の再現・語彙の統一・同一性の判定・数値の保存——**決定論的に解ける問題を
LLMに渡すと、検証できないぶんだけ確実に悪くなる。**

境界の引き方は、たぶんドメインごとに違う。ただ「その出力が正しいことを、
どうやって確かめるつもりか」を先に決めてから使う範囲を決める、という順序は
どこでも同じだと思う。
